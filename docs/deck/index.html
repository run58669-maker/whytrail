WhyTrail

An agent that explains why a metric changed, and shows the query behind every number.

Team: Wei Fang Solo (one builder)

WhyTrail1 / 9

Problem & target users

"Why did the number change?" is the question nobody can answer with evidence

  • Operations analyst, Monday morning: "Manhattan taxi trips dropped last week. Why?"
  • The answer lives in three places that do not share a schema: trip data, weather, calendar.
  • Today's options: a dashboard that shows that it dropped, or an LLM that guesses why.
  • Neither shows the query behind the number. Neither can be audited.

Target user

Operations / BI analysts who must answer "why" with numbers someone else can check: SQL, source tables, row counts.

What they need

Competing explanations tested against the data, the losers shown as well as the winner, and every figure traceable to a query.

WhyTrail2 / 9

Solution

Falsification-first: try to kill every explanation before you believe one

WhyTrail does not ask the model "why?". It asks the data "which explanations survive?"

  • 1. List competing hypotheses: holiday, weather, price, data gap, local-vs-citywide.
  • 2. Run a query designed to refute each one (Zetaris, federated).
  • 3. A Skeptic attacks the survivors: it names a follow-up test from a fixed catalog and the orchestrator runs exactly that test.
  • 4. A Verifier re-derives the two headline totals through an independent Zetaris query; a mismatch blocks the answer.
  • 5. Only then is the answer written, and every figure links to a fact: SQL, source tables, row count, result hash.

Output = answer + why-trail

The prose answer, the list of hypotheses with supported / refuted verdicts, the Skeptic's follow-up result, the Verifier lines, and an evidence ID per claim.

f_b668b44f81 → SQL + tables + rows + hash in logs/world-<run>.jsonl

Agent workflow / architecture

Six agents in a bounded loop, not a fixed chain

question → Orchestrator (bounded state machine, JSONL trace)
  H-MEM hydrate (Meterless) → Planner: hypotheses, each with a falsifying test
  Retriever: SQL templates → Zetaris REST → World Model (provenance per fact)
  Analyst: deterministic verdict per hypothesis (supported / refuted)
  Skeptic: strongest alternative + follow-up test from FOLLOWUP_TESTS
       isolate_daytype    : federated join NY_TAXI x NOAA_GHCN x REF, weekday-matched
       baseline_variation : total of the period before A; ordinary variation?
       → back to Retriever; a failed hypothesis is downgraded: needs_revision
  Verifier: second Zetaris query re-derives the two headline totals (A, B);
       a mismatch blocks the Writer and replaces the number
  Writer: answer + why-trail from World Model payloads only
  H-MEM mine: verdicts persisted for the next run
  • Planner, Skeptic, Writer call the model through one injected generator.
  • Retriever, Analyst, Verifier are plain code: numbers never come from model text.
  • Real back-edges: Skeptic → Retriever; Verifier can block the Writer; H-MEM changes the next Planner run.
  • Every step is a line in logs/trace-<run_id>.jsonl: agent, action, fact ID, elapsed time.

Technical stack · how Zetaris and Meterless were used

Zetaris for every fact, Claude for judgement, Meterless engines for state

Zetaris Lightning SQL data harness

  • Direct REST API POST /api/v1.0/sql-editor/sqls/run: bearer key, X-Org-ID, UUID request IDs, one statement per call.
  • Three sources with qualified names: NY_TAXI.taxi_daily, NOAA_GHCN.central_park_daily, REF.us_holidays; the Skeptic's isolate_daytype test is a federated join across all three.
  • Dataset reproducible from scripts/zetaris/ (export, clean, register).

Meterless agent engines, in-repo

  • World Model: WorldStore, IngestPipeline (idempotent, provenance), ContextBuilder. Evidence ledger: written by Retriever/Analyst/Verifier, read by Skeptic/Writer.
  • H-MEM: MemoryStore (layers, supersede, persist), MemoryRetrieval (hybrid score, retrievalReason). Schema facts + verdicts across runs; read by the Planner.
  • Engines never call a model.

Claude

  • claude-opus-5-5 via the Anthropic SDK behind one injected generator; deterministic mock generator for offline sample mode.

Runtime & tooling

  • Python 3.11+, CLI python -m whytrail and HTTP POST /run, Dockerfile, 21 unit tests, SAMPLE_MODE=true fallback.
  • Built in Cursor (.cursor/rules/whytrail.mdc; Cursor commits tagged [cursor]).

Innovation · what was unique about our sponsor use · honest limits

The model proposes what could be false; Zetaris decides

  • Evidence is a first-class object. Every number in the answer resolves to a World Model fact with SQL, tables, row count and hash. No fact, no sentence.
  • Zetaris closes its own loop. The two headline totals are queried twice with two formulations (template aggregate vs raw rows summed client-side); the Verifier is an independent reader of the same federated data.
  • The Skeptic's follow-up is itself a federated query: NY_TAXI × NOAA_GHCN × REF, weekday-matched, inside Zetaris, not stitched in Python. The Skeptic names the test; the orchestrator runs exactly that and traces it.
  • H-MEM measurably changes behaviour: same question twice in sample mode, 20 queries cold, 10 warm (schema discovery skipped, refuted hypotheses cited from memory). examples/run1_cold_memory.txt, run2_warm_memory.txt.
  • Numbers never come from model text.

Honest limits (kept consistent with the repo)

  • Fixed catalogs: 5 hypotheses, 2 follow-up tests (isolate_daytype, baseline_variation). The model chooses, it does not invent.
  • SQL restricted to templates on three tables; question parser fixed to taxi trips, a borough, two ISO-dated weeks.
  • Verifier re-derives the two headline totals only; other numbers carry provenance, not a re-derivation.
  • Sample mode = synthetic Jan 2024 data, not real TLC/NOAA. Live range 2024-04-01..2025-02-28; weather through 2025-02-05.
  • One recorded live run (run-b5402d4e), made before the follow-up catalog existed: its Skeptic asked for isolate_daytype, the only test then available.
  • NVIDIA not used yet. Cursor = dev environment, not runtime.
